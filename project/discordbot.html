BoTokard : Moteur Communautaire Asynchrone

Bot Python asynchrone multi-flux connecté à Discord, Twitch, Google Gemini et MySQL, hébergé 24/7 sur une machine virtuelle Proxmox VE dédiée.

Production 24/7 Python 3 & Discord.py AsyncIO & aiomysql VM Proxmox VE
← Tous les projets

1. Pourquoi ce projet ? L'évolution d'un simple script

Origine du projet

À la base, BoTokard était un petit script codé pour faire rire mes potes sur un serveur Discord et annoncer les lives Twitch de notre groupe. Mais très vite, j'ai voulu en faire un vrai terrain d'expérimentation pour apprendre ce que je n'apprenais pas à l'école : la concurrence asynchrone, la persistance SQL transactionnelle et l'administration système Linux.

Au fil des mois, le bot a grossi : jeu de cartes TCG avec économie virtuelle, intégration de l'IA Google Gemini pour répondre aux membres, système de modération automatique avec logs d'audit. Pour qu'il tourne sans coupure, je l'ai migré de mon PC personnel vers mon propre serveur physique sous Proxmox VE.

2. Architecture du système & Pipelines d'événements

Infrastructure Linux & Async

Le bot orchestre cinq composants critiques au sein d'une boucle d'événements unique (AsyncIO event loop) :

Flux A
Discord Gateway
Connexion WebSocket bidirectionnelle avec Discord. Réception des interactions boutons, commandes slash et messages utilisateurs en temps réel.
Flux B
Webhooks Twitch
Serveur HTTP interne recevant les alertes EventSub (lancement de live, stream offline) avec validation de signature HMAC-SHA256.
Flux C
Buffer IA (Gemini)
File d'attente intelligente avec rate-limiting par salon et par utilisateur pour interroger l'API Gemini sans épuiser les quotas ni bloquer les autres commandes.
Flux D
Pool MySQL (aiomysql)
Gestion de l'inventaire TCG et des logs d'audit avec pool de connexions asynchrones et transactions strictes (anti-duplication de monnaie).

3. Les Défis Techniques Rencontrés & Mes Solutions

Comment garder un bot rapide, stable et sécurisé avec des centaines d'utilisateurs simultanés.

Défi 01 · Intégrité SQL

Éviter la duplication d'objets lors d'échanges simultanés

Le Problème :

Si deux utilisateurs échangeaient une carte ou si quelqu'un spammait le bouton de confirmation en double-cliquant très vite, deux requêtes asynchrones parallèles lisaient le même inventaire avant que la mise à jour ne soit écrite, créant des doublons gratuits.

Ma Solution :

Utilisation de vraies transactions MySQL avec verrouillage pessimiste : SELECT ... FOR UPDATE à l'intérieur d'un bloc transactionnel atomique (ACID). Si l'une des vérifications échoue, un ROLLBACK complet annule tout.

Défi 02 · Concurrence Async

Ne jamais figer le heartbeat WebSocket de Discord

Le Problème :

L'API Google Gemini peut mettre 2 à 4 secondes à générer une réponse détaillée. Si cette requête était exécutée de manière synchrone, elle bloquait le thread principal Python et Discord déconnectait le bot pour cause de timeout de battement de cœur (heartbeat).

Ma Solution :

Délégation systématique des opérations bloquantes dans des tâches d'arrière-plan avec asyncio.create_task() et asyncio.to_thread() pour les appels HTTP tiers, libérant instantanément la boucle Discord.

Défi 03 · Réseau & Webhooks

Recevoir les webhooks Twitch sur une machine virtuelle interne

Le Problème :

Twitch EventSub nécessite une URL HTTPS publique valide pour envoyer ses notifications de live. Mon serveur Proxmox est situé derrière un routeur local privé avec une adresse IP non fixe.

Ma Solution :

Mise en place d'un reverse proxy sécurisé avec certificat SSL Let's Encrypt et vérification cryptographique rigoureuse de la signature Twitch-Eventsub-Message-Signature (HMAC SHA-256) avant tout traitement de payload.

Défi 04 · Haute Disponibilité

Survie aux coupures et redémarrage automatique sous Linux

Le Problème :

En cas d'exception non gérée ou de redémarrage automatique du serveur pour mise à jour du noyau Linux, le bot ne devait pas rester éteint jusqu'à ce que je m'en rende compte manuellement.

Ma Solution :

Configuration d'une unité systemd personnalisée sur la VM Debian avec directive Restart=always, temporisation exponentielle, capture des signaux d'arrêt propres et redirection des logs vers journald.

bot/cogs/economy/trade_service.py Python (AsyncIO) 
# Transaction atomique sécurisée pour l'échange de cartes TCG
async def execute_secure_card_trade(pool, sender_id: int, receiver_id: int, card_id: int):
    async with pool.acquire() as conn:
        async with conn.cursor() as cursor:
            # 1. Début de la transaction avec isolation stricte
            await conn.begin()
            try:
                # 2. Verrouillage de la ligne pour empêcher les attaques par concurrence (Row Locking)
                await cursor.execute(
                    "SELECT quantity FROM user_inventory WHERE user_id = %s AND card_id = %s FOR UPDATE",
                    (sender_id, card_id)
                )
                row = await cursor.fetchone()
                if not row or row[0] < 1:
                    raise ValueError("Quantité de carte insuffisante ou inexistante.")

                # 3. Débit chez l'émetteur
                await cursor.execute(
                    "UPDATE user_inventory SET quantity = quantity - 1 WHERE user_id = %s AND card_id = %s",
                    (sender_id, card_id)
                )

                # 4. Crédit chez le récepteur (Upsert avec gestion d'existence)
                await cursor.execute(
                    "INSERT INTO user_inventory (user_id, card_id, quantity) VALUES (%s, %s, 1) "
                    "ON DUPLICATE KEY UPDATE quantity = quantity + 1",
                    (receiver_id, card_id)
                )

                # 5. Validation atomique de l'opération
                await conn.commit()
                return True
            except Exception as err:
                # En cas d'erreur ou d'interruption : rollback total, aucune perte
                await conn.rollback()
                logger.error(f"Transaction échouée : {err}")
                raise

Ce que ce projet m'a appris en autodidacte

  • • La gestion de la concurrence : Développer un bot actif apprend très vite que le code synchrone classique ne tient pas la charge dès que plusieurs personnes cliquent en même temps.
  • • L'administration système pratique : Configurer une VM Debian sous Proxmox, créer des services systemd fiables et gérer la sécurité des accès m'a donné des compétences serveur bien plus solides que de la simple théorie.
  • • La rigueur des bases de données : Comprendre le fonctionnement interne des transactions SQL et des verrous de lignes évite des bugs catastrophiques de corruption de données.
