The Infinite Botnet (Reboot) : Moteur & Architecture

Moteur de simulation réactif découplé sur Web Worker, développé en TypeScript sous Vite avec boucle déterministe et synthèse sonore procédurale.

Prototype Jouable TypeScript & Vite Architecture Web Worker Boucle 60Hz Déterministe

1. Pourquoi ce projet ? Un laboratoire de performance dans le navigateur

Laboratoire Technique

J'ai toujours aimé les jeux incrémentaux de simulation de systèmes (comme Universal Paperclips ou Cookie Clicker). En apparence, ce sont des interfaces simples avec des chiffres qui montent. Mais sous le capot, dès que le joueur accumule des centaines d'améliorations et des millions d'entités, le navigateur doit exécuter des millions de calculs par seconde.

Si on fait tourner ces calculs sur le thread principal JavaScript (UI Thread), l'écran saccade, les animations ralentissent et la page ne répond plus. J'ai donc développé ce simulateur comme un défi d'architecture : découpler totalement le moteur mathématique dans un Web Worker indépendant pour garantir 60 FPS constants sur l'écran quoi qu'il arrive.

2. Architecture Multi-Thread : UI vs Web Worker

Pattern Producteur-Consommateur

Deux threads distincts communiquent via un canal de messages typés asynchrones (PostMessage) :

Thread 1 (UI)
Rendu Réactif (React 18)
Gère uniquement l'affichage, les événements souris/clavier et les transitions CSS à 60 FPS. Ne fait aucun calcul d'économie directement.
Pont de Données
Canal Typé PostMessage
Échange de paquets de données sérialisées (actions utilisateur vers le worker, instantanés d'état vers l'UI) avec clonage structuré.
Thread 2 (Worker)
Boucle Déterministe 60 Hz
Accumulateur delta-time : calcule la propagation du botnet, les revenus, la chaleur FBI et la simulation offline sans jamais figer l'écran.
Module Audio
Synthèse Web Audio
Génération d'ondes sonores procédurales en direct (bips, buzzers d'alarme) sans charger le moindre fichier MP3 externe.

3. Les Défis Techniques Rencontrés & Comment je les ai résolus

Les contraintes de calcul haute fréquence dans le moteur JavaScript V8.

Défi 01 · Isolation des Threads

Séparer les calculs mathématiques de l'interface utilisateur

Le Problème :

Dans un jeu incrémental avec des dizaines de modules actifs en parallèle (scanners d'IP, exploits de bots, bourse de dark money), les boucles de calcul consomment trop de temps CPU sur un seul thread. Résultat : les clics sur les boutons ne répondent plus immédiatement.

Ma Solution :

Déportation de 100% de l'état de jeu dans un Web Worker dédié. Le composant React reçoit uniquement un snapshot de l'état toutes les 16ms et se contente de l'afficher, garantissant une fluidité absolue.

Défi 02 · Temps & Cadence

Empêcher la dérive temporelle quand l'onglet est masqué

Le Problème :

Les navigateurs modernes réduisent drastiquement la fréquence de setInterval (jusqu'à 1 seule exécution par seconde) lorsque l'onglet n'est plus visible pour économiser la batterie. Le jeu tournait alors au ralenti.

Ma Solution :

Pattern de boucle par accumulateur delta-time (performance.now()). À chaque réveil, le moteur calcule le temps réel écoulé depuis la dernière mise à jour et rattrape exactement le nombre d'itérations nécessaires par tranches fixes de 1/60e de seconde.

Défi 03 · Données & Portabilité

Sauvegarde robuste et export sans risque de corruption

Le Problème :

Si le joueur recharge la page pendant une sauvegarde ou si la structure des données change lors d'une mise à jour de code, une ancienne sauvegarde peut faire crasher le moteur au démarrage.

Ma Solution :

Sérialisation de l'état avec numéro de version de schéma explicite (schemaVersion: 2), encodage Base64 pour l'export portatif et pipeline de migration automatique qui applique des patches de transition si un schéma ancien est détecté.

Défi 04 · Son & Légèreté

Créer des bruitages immersifs avec zéro mégaoctet d'assets audio

Le Problème :

Télécharger des dizaines de fichiers MP3/WAV alourdit considérablement le chargement du site et pose des problèmes de droits d'auteur ou de latence de lecture audio.

Ma Solution :

Utilisation directe de l'API Web Audio native : un synthétiseur logiciel autonome crée des oscillateurs (formes d'ondes carrées, en dents de scie) modulés par des nœuds de gain (enveloppes ADSR) pour générer des bips cybernétiques ultra-rapides à coût zéro en bande passante.

src/simulation/engine-worker.ts TypeScript 
// Boucle déterministe avec accumulateur fixe dans le Web Worker
const TICK_RATE_MS = 1000 / 60; // 60 Hz cadence fixe
let lastTime = performance.now();
let accumulator = 0;

function simulationLoop() {
  const currentTime = performance.now();
  let delta = currentTime - lastTime;
  lastTime = currentTime;

  // Plafond de sécurité pour éviter la "spirale de la mort" si le thread s'endort longtemps
  if (delta > 2000) delta = 2000;
  accumulator += delta;

  // Exécuter autant de pas discrets que nécessaire pour rattraper le temps réel
  while (accumulator >= TICK_RATE_MS) {
    stepSimulation(TICK_RATE_MS / 1000);
    accumulator -= TICK_RATE_MS;
  }

  // Émettre un instantané léger vers le thread principal pour mise à jour UI
  postMessage({ type: 'TICK_SYNC', payload: getSerializableState() });
  requestAnimationFrame(simulationLoop);
}

Ce que ce projet m'a appris en autodidacte

  • • L'architecture multi-thread dans le web : Les Web Workers permettent de transformer le navigateur en véritable environnement de calcul distribué, bien au-delà de simples pages statiques.
  • • La gestion de la mémoire et du garbage collector : Créer des milliers d'objets par seconde dans une boucle rapide déclenche le garbage collector et crée des micro-gelures d'écran. Réutiliser les objets (object pooling) résout ce problème.
  • • La puissance des APIs natives : L'API Web Audio et l'API Worker permettent de faire des applications complexes et immersives sans avoir besoin de bibliothèques externes lourdes.
